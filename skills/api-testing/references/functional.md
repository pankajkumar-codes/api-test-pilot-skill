# Functional testing: smoke, positive, negative, edge

Generated by `scripts/gen_pytest.py` (types `smoke`, `positive`, `negative`, `edge`). Input is the intake JSON
(`references/intake.md`); output is readable pytest you can edit. Boundaries between the types, so nothing is tested twice:

| Type | Question | Does NOT cover |
|------|----------|----------------|
| smoke | Is every safe GET reachable and 2xx? | bodies, auth, bad input |
| positive | Does a valid request give the documented status, JSON and echoed key fields? | invalid input |
| negative | Are missing credentials, unknown ids, malformed JSON, wrong content type rejected with a documented error shape? | per-field constraints (data-validation) |
| edge | Do boundaries, unicode, empty/huge values and nulls behave (accepted or cleanly rejected, never a 5xx)? | schema violations (data-validation) |

## Generate and run
```
python scripts/intake.py openapi.yaml -o intake.json
python scripts/gen_pytest.py intake.json -o api_tests --types smoke,positive,negative,edge
APITEST_BASE_URL=http://localhost:8080 APITEST_BEARERAUTH_TOKEN=... python -m pytest api_tests -v -ra
```
The generator prints the exact rerun command. The suite is `conftest.py` + `apitest_runtime.py` (helpers, copied) +
`endpoints.py` (the endpoint table with valid baseline requests) + `test_<type>.py`.

## Expectations the generated tests encode
- **Positive**: status in the documented 2xx set; JSON body parses when documented as JSON; fields sent that the
  response also returns must come back unchanged (`expect_echo`).
- **Negative**: no credentials -> 401/403; unknown id -> 404 (exactly 404 only if the spec documents it, else any 4xx;
  for PUT/DELETE, which may legitimately upsert or be idempotent, only "no 5xx" unless 404 is documented);
  malformed JSON / wrong content type / empty required body -> 4xx; error body validated against the documented error schema.
- **Edge**: unicode must round-trip; special characters, empty strings, nulls, `int64` overflow and 100k-character
  strings must not 5xx; documented min/max boundaries must be accepted. A 5xx is always a finding (MEDIUM).

## Data the tests need (environment variables)
- Credentials: names are listed in `conftest.py` and by `intake.py` (`APITEST_<SCHEME>_TOKEN|USER|PASS|KEY`). Never ask for values in chat.
- Existing ids for path parameters: `APITEST_PATH_<PARAM>` (or the spec `example`). Without one the test **skips and says which variable to set**.
  The integration flows (`references/integration.md`) create their own data and need none.
- `APITEST_ALLOW_DESTRUCTIVE=yes` is required for any DELETE against an existing id; the test consumes that id.
- Non-local targets need `APITEST_TARGET_ENV` (local/dev/staging/prod...). Tests never guess a production URL.
- Administrative endpoints (`/admin`, tag `admin`) skip success-path tests when `APITEST_ASSUME_NON_ADMIN=yes`.

## Side effects
Positive/edge tests for POST/PUT/PATCH create or modify data in the target. Use a test environment. Say so in the plan.

## Not generated (reported as notes)
Request bodies other than JSON and urlencoded forms (multipart, XML) are listed in the generator output, not guessed.

## Extending
Edit the generated files freely, or change a generator in `scripts/gen_functional.py` and regenerate (regeneration overwrites).
