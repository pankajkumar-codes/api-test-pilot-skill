# Data validation

Generated by `gen_pytest.py --types data-validation` (`scripts/gen_validation.py`) into `test_data_validation.py`.
Each case sends an otherwise valid request with exactly ONE violation and expects a **4xx rejection** with the documented
error shape. Accepting the value (2xx) is a finding; a 5xx is a worse one.

| Violation | Derived from |
|-----------|--------------|
| missing required field | `required` of the request schema (and required query params) |
| wrong JSON type | `type` of each property (string<-number, integer<-"abc", boolean<-"maybe", array<-string, object<-string) |
| value not in enum | `enum` (body and query) |
| bad format | `format`: email, uuid, date, date-time, uri, ipv4 |
| too short / too long | `minLength` / `maxLength` |
| below / above range | `minimum` / `maximum` (exclusive bounds respected) |
| too few / too many items | `minItems` / `maxItems` |
| unexpected property | only when `additionalProperties: false` |
| non-numeric path/query value | integer/number parameters; `minimum`/`maximum` of query parameters |

Notes
- `pattern` is not mutated (an invalid string cannot be derived reliably); add cases by hand.
- Format and enum checks fail on APIs that document a constraint but do not enforce it. That is the point; if the
  spec is wrong instead, fix the spec and rerun.
- Boundary values that must be **accepted** live in the edge tests, not here.
- Valid-value assertions (types, ranges of responses) are contract tests (`references/contract.md`).
- Same environment variables and side-effect rules as `references/functional.md`.
